# 个人记录与反馈

## 反馈闭环（M2-B04）

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/feedback/` | 仅列出当前账号反馈，按创建时间、UUID 倒序分页；支持项目标准 `page`、`page_size` |
| `POST /api/v1/feedback/` | 提交 `body`，去掉首尾空白后须为 1～1000 字符；初始为待处理 |
| `DELETE /api/v1/feedback/<UUID>/` | 删除本人反馈；他人或已删除的反馈返回 404 |

接口需登录，不支持公开检索他人反馈。详情不开放 GET、PATCH 或 PUT，不能修改原文、状态和管理员答复。提交时在事务内锁定并重新检查有效账号，拒绝认证后已注销或被停用的旧账号快照。

返回字段固定为 `id/body/status/created_at/reply/resolved_at`。客户端不能设置反馈 ID、归属、处理状态、答复、处理时间和处理人。状态为 `pending` 时，即使后台保存了答复草稿，也返回 `reply: ""`、`resolved_at: null`。状态为 `resolved` 时向本人展示答复和处理时间，处理人信息始终仅管理端可见。

历史已处理记录可能没有答复和处理时间；本次迁移只增加字段，保留其原有 `resolved` 状态。前端应提示“历史记录未提供答复/处理时间”，不可假定已有具体答复。

### 管理端处理

- 需要 `activity.change_feedback` 权限才能处理；仅有查看权限的管理员不能提交处理操作，管理端也不能代替用户新建反馈。
- 归属用户、反馈正文、创建时间、处理时间和处理人只读。管理员可编辑处理状态及最多 1000 字符的答复。
- 保存为已处理时必须提供有效答复；首次处理或修改答复时自动记录当前处理人、处理时间。重复保存未修改的答复保留原处理时间和处理人。
- 重新打开为待处理会清空处理时间和处理人；保留的答复文字属于草稿，不再向用户显示。历史已处理记录再次保存时也需要补齐答复。
- Django 管理端 `LogEntry` 记录操作人、对象及变更字段；不将正文或答复内容附加到变更日志。
- 用户注销会级联删除其全部反馈；处理管理员被删除时仅清空处理人关联，保留其他用户的反馈及已发布答复。
