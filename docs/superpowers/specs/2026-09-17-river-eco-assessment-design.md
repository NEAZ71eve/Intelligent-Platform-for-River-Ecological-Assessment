# 河道生态评估模块设计（HYHQ 演进）

版本：v1.0
日期：2026-09-17
状态：设计已获用户批准，待实现计划
上游文档：HYHQ 仓库 `docs/开发方案稿.md`（v0.1）、`inference/README.md`
关联仓库：https://github.com/gruTGU/HYHQ（演进基础，非本仓库）

## 1. 背景与定位

HYHQ（海晏河清智慧平台）已完成 M1 基础版与 M3 五类花卉图像识别，具备 Django+DRF+PostgreSQL 后端、原生微信小程序、ONNX CPU 推理工作进程、模型登记/版本/回退机制。本设计将平台识别方向从"花卉分类"演进为"河道生态评估"：

- 巡河工作人员上传**定位 + 河道图像**
- 服务端运行 YOLO 检测模型识别 4 类生态问题目标
- 规则引擎输出**单图生态评估**：检测框 + 问题清单 + 生态等级 + 规则式原因分析
- 定位关联河段，结合该河段历史指标辅助原因分析

本模块在 HYHQ 仓库内开发；本地 `miniprogram-2`（TDesign demo）仅作组件素材参考，不承载业务代码。

## 2. 已确认决策记录

| 决策项 | 结论 |
| --- | --- |
| 开发策略 | 演进 HYHQ 仓库，保留后端/队列/模型管理/数据契约，前端沿用原生小程序 |
| 目标用户 | 巡河工作人员 |
| 检测类别 | 4 类：水面漂浮物 / 水华黑臭水体 / 排污口污水直排 / 岸带环境问题 |
| 评估输出 | 单图评估（不做河段聚合，列为 V2 候选） |
| 原因分析 | 规则式（确定性推断），不用 LLM |
| 定位用途 | 关联河段记录（匹配水体/监测站，结合历史指标） |

| 回退条款 | 决策门不通过 → 回退花卉识别（保留 M3 全部能力） |
| 技术方案 | 方案 A：YOLOv8n + ONNX CPU 推理（演进现有链路） |

## 3. 系统架构

**保留不动**：Django+DRF+PostgreSQL；鉴权/会话/受控上传/文件过期清理；任务队列 + 推理工作进程 + 单机执行锁；模型登记/版本/回退；Django Admin；来源标注体系（api/dataset/simulation/manual）。

**改造**：识别模块从"分类"语义升级为"检测+评估"语义（任务与结果 schema 扩展）；小程序"AI 识别"入口改为"河道巡查"。

**新增**：评估规则引擎（规则集版本化入库）；定位→河段关联逻辑。

## 4. 数据流水线（D0–D3）

- **D0 决策门（最先执行）**：通过 Frontiers 论文数据可用性声明/通讯作者验证 WATER-DET 能否实际下载。获取失败即触发回退条款，转为花卉识别方案，后续阶段取消。
- **D1 类别体系**：两层设计。
  - 评估大类（4）：`floating_debris` / `bloom_blackwater` / `outfall_discharge` / `bank_problem`
  - 原始细粒度标签：bottle、foam、plastic、水草、藻类、污水黑灰水色、泡沫污染、排污口、岸线垃圾、岸线侵占等
  - 训练用细类（保留判别信息），评估聚合到大类；跨数据集映射表落地为版本化配置文件
- **D2 训练**：ultralytics YOLOv8n，640×640 输入；数据组合为 IWHR + YRDG + FloW-Img + TU Delft Green Village + WATER-DET；dHash 去重后按图划分（不跨集合），训练/验证/测试划分冻结；训练在开发电脑执行，服务器只推理。
- **D3 制品**：ONNX 导出 + manifest 登记（沿用 HYHQ 登记校验机制，schema 扩展支持检测框输出契约）；产出模型评估报告：mAP50 / mAP50:95、逐类精确率召回率、混淆矩阵、CPU 推理延迟、失败样例。

## 5. 类别体系与数据集映射

| 数据集 | 贡献的细类 | 映射到评估大类 |
| --- | --- | --- |
| IWHR_AI_Lable_Floater_V1（主力） | bottle / foam / 水草 / 藻类等 | 水面漂浮物（主力） |
| YRDG / FloW-Img / TU Delft | 塑料/纸/玻璃/金属/织物/瓶类等 | 水面漂浮物（补充） |
| WATER-DET | 污水黑灰水色 / 泡沫污染 / 排污口 / 岸线垃圾 / 岸线侵占 | 水华黑臭 + 排污口 + 岸带问题 |

IWHR_AI_Lable_Floater_V1 定位说明：3,000 图 / 23,692 标注对象，中国水科院发布（Scientific Data 2025，CC BY），北京大运河段岸基视角拍摄，与巡河员手机拍摄场景最接近，是"水面漂浮物"大类的主要支撑。论文基准表明该任务小目标多、光照复杂，预期 mAP 低于常规检测场景，报告中如实呈现。

## 6. 后端设计

- **任务资源**：演进为 `/api/v1/assessment-jobs`。请求携带图像与经纬度；结果携带检测框列表（类别、置信度、归一化坐标、面积占比）。
- **河段关联**：服务端用经纬度匹配水体/监测站。首版采用"最近监测站 + 行政区划"简化判定，不实现真实地理围栏；匹配失败时允许用户手动选择河段。
- **评估规则引擎**：规则集（RuleSet）版本化入库；任务结果固定记录所用规则版本；规则更新不回写历史结果。
- **原因分析**（确定性规则示例）：
  - 漂浮物密集 + 岸带垃圾并存 → "周边垃圾清运/倾倒管控问题"
  - 检出水华 + 模拟水温偏高 → "富营养化倾向，建议核查上游氮磷来源"（涉及模拟数据必须标注）
  - 检出排污口/水色异常 → "疑似污水直排，建议溯源排查"
- **任务状态机**：沿用 `queued / running / succeeded / failed` + 稳定错误码；超时、无模型、低图质均明确失败或降级，不输出伪造结论。
- **推理资源约束**：沿用单工作进程、CPU 单线程、执行超时（默认 10 秒，可配 1–60 秒）、全局队列上限。

## 7. 小程序页面设计

```
首页（保留：天气/示范区概况，入口改为"河道巡查"）
生态导览（不动）
河道巡查（原 AI 识别入口改造）
├─ 巡查上报页：拍照/相册选图（复用现有上传逻辑）
│   + 定位卡片（当前经纬度 → 匹配河段名，支持手动改选）
│   + 提交按钮
├─ 评估结果页：原图 + 检测框叠加（canvas 绘制）
│   + 生态等级徽章（优/良/中/差）
│   + 问题清单（类别/数量/面积占比）
│   + 原因分析卡片 + 该河段近期指标（水温/pH/浊度/DO，标注模拟）
│   + 免责声明（"平台演示评分"，非官方水质评价）
└─ 巡查记录列表：按河段分组、时间倒序，可回看结果
科普智游（不动，评估结果继续关联科普内容）
我的（新增"我的巡查记录"入口）
```

低图质、低置信度沿用现有 `LOW_IMAGE_QUALITY` / `LOW_CONFIDENCE` 协议展示。

## 8. 评估规则引擎（RULE v1）

- 100 分制扣分：
  - 漂浮物：按检出数量与总面积占比阶梯扣分
  - 水华/黑臭：按覆盖面积占比扣分
  - 排污口/污水直排：检出即重扣
  - 岸带问题：按类别加权扣分
- 等级映射：优 ≥85 / 良 70–84 / 中 50–69 / 差 <50
- 无检测目标且图片质量合格 → 优；低图质 → 不输出等级（沿用低图质协议）
- 命名约束（遵循 HYHQ 方案稿 2.3 节）：明确称"平台演示评分"，不输出官方水质类别；规则公式、权重、版本公开可查
- 评估报告附该河段近期模拟指标（水温/pH/浊度/溶解氧），均标注模拟来源

## 9. API 契约

```
POST /api/v1/assessment-jobs          {image, lat, lng} → {job_id, status}
GET  /api/v1/assessment-jobs/{id}     → {status, grade, issues[], causes[], detections[], rule_version, water_body, disclaimer}
GET  /api/v1/assessment-jobs?water_body={id}  → 历史记录
```

错误格式、鉴权、分页、时间格式与现有 `/api/v1/` 约定一致。

## 10. 验收标准

1. D0 决策门通过：WATER-DET 实际获取并完成质量核验
2. 模型报告基于独立测试集（不使用训练指标）；CPU 单图推理 ≤10 秒
3. 真机完整流程可演示：拍照 → 定位 → 评估 → 等级 → 原因 → 记录
4. 规则版本、数据来源、模拟标注全部可追溯（沿用 HYHQ 验收口径）
5. 失败路径（无模型、超时、低图质、回退态）均可明确演示

## 11. 风险与回退

| 风险 | 应对 |
| --- | --- |
| WATER-DET 不可获取 | 触发回退条款：水华黑臭/排污口/岸带三类无合格替代来源，转为花卉识别方案，M3 能力保留 |
| 排污口样本量少（约 150） | 首版接受较低召回，模型报告中明示；预留自采数据补充通道 |
| 单图评估局限 | 免责声明固定展示，不做官方结论；河段聚合列为 V2 |
| 检测精度低于花卉分类 | 属预期（IWHR 基准已证明任务难度），报告如实呈现逐类指标 |

逐类质量评估：

| 检测类别 | 数据支撑 | 评估 |
| --- | --- | --- |
| 水面漂浮物 | IWHR（主力）+ YRDG + FloW + TU Delft，可组合超 1.8 万图 | 充足 |
| 水华/黑臭水体 | 仅 WATER-DET：污水黑灰水色（150）+ 泡沫污染（150） | 薄弱，单一来源 |
| 排污口/污水直排 | 仅 WATER-DET 的 sewage outfall 类 | 薄弱，单一来源 |
| 岸带环境问题 | WATER-DET 岸线垃圾/岸线侵占 + RoLID-11K 参考 | 薄弱，单一来源为主 |

决策门结论：**有条件通过**。第一优先行动为验证 WATER-DET 获取渠道；获取成功则方案成立，失败则触发回退花卉识别。

评估维度数据说明：生态等级由检测结果的类别权重 + 数量 + 面积占比规则计算（RULE v1），参照《地表水环境质量标准》GB 3838-2002 框架表述；河段历史指标沿用 HYHQ 现有模拟数据体系并标注来源。
