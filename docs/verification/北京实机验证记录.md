## 发现并修复的问题

### 1. 私有图片缓存标记被覆盖

视图设置 `private, no-store`，统一响应处理随后覆盖为 no-store。本轮改为合并缓存指令，保留 private；覆盖原图、缩略图、匿名与跨账号响应测试。

### 2. 合法大图造成内存压力与超时

旧上传流程在缩小之前创建多份 2000 万像素图像；实机 API 内存达到约 406MiB 并触发 MemoryHigh 回收，处理约 21 秒，超过测试请求期限。

修复后先限制像素副本尺寸，再旋转、白底合成与重编码，显式关闭中间图像。仍接受原有 2000 万像素上限，保留方向、透明图片白底、元数据剥离和输出尺寸契约。API 采用单线程，MemoryHigh 384MiB / MemoryMax 512MiB，禁用该服务 swap。

实际同时提交两张 5000×4000 RGBA PNG（每张 87,796 字节）：

- 两次均 201，分别 **803ms / 1506ms**；删除与账户清理验证通过。
- API 整个 cgroup 峰值 **266,743,808 字节，约 254MiB**；检查结束当前占用约 57MiB。
- 无 OOM 或 API 自动重启。

原始汇总：[大图 JSON](beijing/hyhq-large-upload.json)。这是固定合成样本的边界验证，不表示所有图片都具有相同耗时。

### 3. 解码期间注销账户产生 500

上传验证较慢时，账户可能在取得写入锁前注销。现改为锁定仍有效的用户，失效时返回 `401 AUTH_REQUIRED`，且不留下文件；新增回归覆盖该竞态。

### 4. 生产 CLI 与文件权限

生产 wrapper 使用独立、受限配置，不继承调用者环境；严格拒绝不支持的环境文件语法，降权后才执行 Django。配置和密钥不进入日志、命令行或仓库。

部署期间一次递归权限调整短暂触发旧运行进程的锁文件 PermissionError；已恢复 var 的 hyhq 所有权并重启消费者。最后服务重启后的冒烟与并发抽测中，三个服务 NRestarts 均为 0。后续在启动前固定目录权限，不在运行中递归更改 var。

测试后的三个服务均 active，NRestarts=0。该轮服务 cgroup 峰值分别约 API 93MiB、花卉 165MiB、河道 181MiB；前述大图峰值属于上一个独立测试周期。测试结束整机可用内存约 1023MiB，磁盘剩余约 34GB。
