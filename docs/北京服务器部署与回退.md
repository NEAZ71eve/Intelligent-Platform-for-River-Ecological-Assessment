本次把已完成的整合版本部署到北京实例，使用模拟生态数据、五类花卉分类和河道漂浮物实验检测。源码基线为 `f31c55f749cfc8ef101df24a8ac37422329b2389`；进行中的 M2 修改不包含在该发布目录中。

记录日期：2026-09-20。本文将已确认的部署事实与后续操作分开列出；命令示例不代表命令已经执行，实际验收结果应以本轮实测记录为准。

域名的 A 记录已解析到本实例，用户确认**备案仍在进行中**。实测公网 HTTP 被腾讯云重定向至拦截页，而服务器本机的 ACME 测试路径可以访问。因此本轮服务器内部测试不能计为公网 HTTPS、微信真机或正式上线验收；不要通过关闭生产安全设置掩盖该状态。

真实 `WECHAT_APP_ID` 和 `WECHAT_APP_SECRET` 尚未配置。生产环境保持 `ENV=production`、`DJANGO_DEBUG=0`、`ALLOW_DEV_AUTH=0`，不启用模拟登录。

## 3. 生产配置和管理命令

所有生产管理命令必须加载与 systemd 相同的环境文件。仓库的开发脚本不会自动加载 `/etc/hyhq/f31c55f.env`，不能直接用它们管理本次生产库。

以 root 登录服务器后，定义本次发布专用函数：

```bash
hyhq_manage() {
  python3 /srv/hyhq-releases/f31c55f/deploy/run-production-command.py \
    --env-file /etc/hyhq/f31c55f.env \
    --release /srv/hyhq-releases/f31c55f \
    manage.py "$@"
}
```

该 wrapper 读取受限配置文件后降权为 `hyhq` 再执行应用命令；不将数据库密码或 Django 密钥放入命令行。配置文件仅支持单行 `KEY=value` 或整值匹配引号；拒绝转义、多行和重复变量，不作为 shell 脚本 `source`。wrapper 不继承调用者环境，固定 Django settings，避免误连开发数据库。

本次关键配置如下，实际密钥和数据库密码只保存在服务器配置文件中：

```dotenv
ENV=production
DJANGO_DEBUG=0
ALLOW_DEV_AUTH=0
HYHQ_USE_SQLITE=0
DJANGO_ALLOWED_HOSTS=greatdata.asia
DJANGO_CSRF_TRUSTED_ORIGINS=https://greatdata.asia
TRUST_PROXY_HTTPS=1
HYHQ_MODEL_ROOT=/srv/hyhq-releases/f31c55f/inference/artifacts
HYHQ_ASSESSMENT_MODEL_ROOT=/srv/hyhq-releases/f31c55f/inference/artifacts
HYHQ_RECOGNITION_TIMEOUT_SECONDS=10
HYHQ_ASSESSMENT_TIMEOUT_SECONDS=10
```

`DATABASE_URL` 必须指向新库 `hyhq_f31c55f`；保留唯一的生产 `DJANGO_SECRET_KEY`。代理必须覆盖 `X-Forwarded-Proto`，API 端口只监听回环地址。不要直接公开 18080、PostgreSQL 或上传文件目录。

初始化顺序如下；本次已经完成迁移、静态文件收集、种子数据及模型登记。以下也可用于核对后续部署步骤：


`seed_demo` 生成模拟数据；跨小时重复运行会增加新的完整快照，不应当作每次服务启动的动作。生产检查中的 HSTS 子域名和 preload 提示需按域名部署范围评估，本轮没有为了清除提示而为尚未验证的子域名开启这些选项。

使用本次专用的 `deploy/beijing/` 单元，避免覆盖原发布单元：

这里只模拟可信反向代理传入的协议头，不建立 TLS 连接；成功说明服务器内部 API 正常，不能说明公网证书正常。

## 5. Nginx 切换操作指南

**本轮已完成以下切换，结果见 [北京实机验证记录](verification/北京实机验证记录.md)。** 后续操作仍需按实际状态逐步核对。 切换前确认新库包含需要保留的数据、两类任务队列已处理完毕，并短暂停止业务写入。原服务和新服务使用不同数据库，切换期间不要让两套服务同时接受用户写入。

先额外保存即将修改的 Nginx 文件，供快速回退：

```bash
test -e /var/backups/hyhq/pre-f31c55f-20260920/hyhq.conf.before-cutover || \
  cp -a /etc/nginx/sites-available/hyhq.conf \
    /var/backups/hyhq/pre-f31c55f-20260920/hyhq.conf.before-cutover
```

将 `/etc/nginx/sites-available/hyhq.conf` 中 API 上游改为 `http://127.0.0.1:18080`，静态文件目录改为 `/srv/hyhq-releases/f31c55f/backend/staticfiles/`。保留 ACME webroot `/var/www/certbot` 和所有代理覆盖头，不添加公开 `/media/` 映射。检查和重载：

```bash
nginx -t
systemctl reload nginx
systemctl enable hyhq-v3-api hyhq-v3-recognition hyhq-v3-assessment
systemctl is-enabled hyhq-v3-api hyhq-v3-recognition hyhq-v3-assessment
# 稍候新进程就绪后核对回环健康，再检查 Nginx（HTTP 应跳转 HTTPS）。
```

原消费者应在启动新消费者前停止；旧 API 在切换窗口停止，最后确认三个旧单元均停用：

```bash
systemctl disable --now hyhq-api hyhq-assessment hyhq-recognition
```

只停上述已确认的原 HYHQ 服务（旧 recognition 已存在但此前未启用）。曾发现另一个监听 `127.0.0.1:18000` 的开发进程，它不属于这些单元，不在本次切换命令中停止。

当前没有可用的公网 HTTPS 链路，生产 HTTP 重定向到 HTTPS 是预期行为。Nginx 的内部路由切换完成也不能解除腾讯云备案拦截。

## 6. 备案完成后的上线步骤

按以下顺序继续，前一步未通过时不要把后续项记为完成：

1. 在腾讯云确认备案完成、接入状态正常且拦截解除；从公网验证 `greatdata.asia` 的 A 记录、80/443 安全组规则及实际可达性。
2. 在 `/var/www/certbot/.well-known/acme-challenge/` 放置临时验证文件，从公网取得预期内容后删除。若仍收到腾讯云拦截响应，先处理域名接入状态。
3. 签发真实证书，再配置 Nginx 443。已有 certbot，可使用下方 webroot 命令；首次运行按实际管理员邮箱完成交互配置。
4. 公网证书验证通过后，运行不带 `--trusted-loopback` 的生产冒烟脚本，`--base-url` 改为 `https://greatdata.asia`。通过公网 HTTPS 调用后才可将对应项记为通过。
5. HTTPS 验证通过后，将 `miniprogram/config/index.js` 中 `baseURL` 设为 `https://greatdata.asia/api/v1`、`development` 设为 `false`。将真实微信 AppID/Secret 写入服务器受限环境文件，重启三项新服务。在微信平台完成小程序所需配置，将 HTTPS 域名配置为相应请求和上传/下载合法域名。
6. 用微信开发者工具及真实手机验证登录、上传、异步结果、私有图片访问、注销和定位隐私授权。模拟账户测试不等于真实微信登录测试。
7. 单独完成约定的 30 分钟负载、资源监控、备份恢复和维护窗口重启验收；记录时长、请求量、延迟、失败数和峰值内存。

```bash
certbot certonly --webroot -w /var/www/certbot -d greatdata.asia
```

证书签发后，可参考 `deploy/nginx.conf.example` 配置 443，但必须使用本次域名、18080 上游和新发布静态目录。证书路径为 `/etc/letsencrypt/live/greatdata.asia/fullchain.pem` 和同目录 `privkey.pem`。80 端口保留 ACME location，对其他路径跳转 HTTPS；Nginx 向后端设置 `X-Forwarded-Proto $scheme`，不能把来自客户端的同名头直接转发。


## 7. 回退步骤

回退将流量切回原 `/srv/hyhq` 和原 `hyhq` 库。**新库切换后产生的数据不会自动合并回原库。** 先停止新增写入，保存新库和新上传文件，再回退；保留新发布和新库以便核对差异。不要用旧备份直接覆盖新库。

以下命令依赖第 5 节保存的 `hyhq.conf.before-cutover`，以 root 在服务器执行：

```bash
# 为本次回退创建单独目录，保存切换后数据。
rollback_snapshot="/var/backups/hyhq/rollback-$(date -u +%Y%m%dT%H%M%SZ)"
install -d -m 0700 "$rollback_snapshot"
runuser -u postgres -- pg_dump -Fc hyhq_f31c55f > "$rollback_snapshot/hyhq_f31c55f.dump"
tar -czf "$rollback_snapshot/new-private-files.tar.gz" \
  -C /srv/hyhq-releases/f31c55f/backend var/private
chmod 0600 "$rollback_snapshot/hyhq_f31c55f.dump" "$rollback_snapshot/new-private-files.tar.gz"

# 先停止新消费者及清理定时器，避免两代模型同时执行。
systemctl stop hyhq-v3-recognition hyhq-v3-assessment hyhq-v3-cleanup.timer
# 原环境文件仍指向原库；恢复原服务，再切换入口。
systemctl start hyhq-api hyhq-assessment
systemctl is-active hyhq-api hyhq-assessment
test -f /var/backups/hyhq/pre-f31c55f-20260920/hyhq.conf.before-cutover
cp -a /var/backups/hyhq/pre-f31c55f-20260920/hyhq.conf.before-cutover \
  /etc/nginx/sites-available/hyhq.conf
nginx -t
systemctl reload nginx
systemctl enable hyhq-api hyhq-assessment
systemctl disable --now hyhq-v3-api hyhq-v3-recognition hyhq-v3-assessment hyhq-v3-cleanup.timer

curl --fail --silent --show-error \
  -H 'Host: greatdata.asia' -H 'X-Forwarded-Proto: https' \
  http://127.0.0.1:8000/api/v1/health/
```

`nginx -t` 失败时不要继续重载，应检查站点文件；上述命令须逐步核对结果，不能忽略失败继续执行。如果后续已增加 HTTPS，优先保留已验证的 HTTPS 配置，只将上游与静态目录改回原发布；不要用早期 HTTP 备份覆盖已运行的 HTTPS 配置。

如果原数据库发生独立故障，可将 `hyhq.dump` 恢复到另一个新库核验：

```bash
# 仅在该恢复库尚不存在时执行；不删除、不覆盖任何现存库。
runuser -u postgres -- createdb -O hyhq hyhq_restore_20260920
runuser -u postgres -- pg_restore --exit-on-error --no-owner --role=hyhq \
  -d hyhq_restore_20260920 < /var/backups/hyhq/pre-f31c55f-20260920/hyhq.dump
```

上面的输入重定向由 root 打开备份文件，再将内容交给 `postgres` 恢复，无需放宽备份目录权限。先验证恢复库，再在维护窗口修改相应受限环境文件的数据库目标；原源码与配置归档只用于定向恢复，不应直接整包覆盖 `/etc` 或 `/srv`。
